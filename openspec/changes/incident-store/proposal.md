## Why

Target capability: `incident-store`.

The remediation loop (stage 4) is an explicit, checkpointed state machine (`Received → Diagnosing → Remediating → Verifying → retry | Escalated | Resolved`); it cannot be built without somewhere durable to persist that state. Without a store, a crashed run has no way to resume instead of restarting, and re-running a destructive remediation on restart is the exact failure the spec calls out to avoid. Incident history also feeds downstream capabilities directly: ChatOps deterministic reads ("which remediation fixed the last crash?"), the eval harness that replays recorded incidents, and (indirectly, via a future indexing step into a still-undecided vector store) the diagnosis agent's RAG layer. Building the store now, ahead of the orchestrator, lets stage 4 be pure state-machine logic against an already-proven persistence contract.

## What Changes

- Add an `Incident` domain model: one incident per Signal-driven remediation attempt, carrying its current lifecycle state, the originating Signal, the resolved Target, and an ordered history of remediation attempts.
- Add a `RemediationAttempt` model: one row per remediation execution, recording the remediation name, an idempotency key recorded **before** execution (not after), start/end timestamps, outcome (`succeeded`, `failed`, `skipped`), free-form diagnosis evidence, and the approval audit trail for that execution (`approval_status` of `not_required`/`pending`/`approved`/`denied`, plus `approved_by` and `approved_at`). Whether a remediation *requires* approval is not stored here; that is a static property of the remediation definition owned by the remediation registry.
- Define the lifecycle states as a closed enum: `received`, `diagnosing`, `remediating`, `verifying`, `escalated`, `resolved`. (The spec's `retry` is not a state — it's a transition back to `diagnosing` or `remediating` after a failed `verifying`.)
- Add a Postgres schema (SQLAlchemy 2.0 Core/ORM) for `incidents`, `incident_transitions` (an append-only log of every state change) and `remediation_attempts`, replacing the dead `alerts` table and commented-out `remediations` table in `yubarta/infra/db/orm.py`.
- Add a three-mechanism concurrency model, kept deliberately separate: an optimistic `version` on `incidents` (transitions are conditional updates that increment it; a mismatch is rejected as a concurrent modification rather than applied), a `lease_generation` fencing token (rejects a write from a Director replica whose lease was superseded, a race `version` cannot detect), and the pre-execution idempotency key on attempts (prevents duplicate *external* execution, which neither of the other two can). None of the three substitutes for another.
- Introduce a Unit of Work scoped to Postgres operations: the conditional state update and its transition record commit or roll back together. External remediation effects are never executed inside a database transaction; record-before-execute compensates.
- Add an `IncidentStore` port (`Protocol`) in `yubarta/domain/ports.py` and a `SqlAlchemyIncidentStore` implementation in `yubarta/infra/db/repository.py`, replacing the current placeholder `SqlAlchemySignalRepository`.
- Store operations: create an incident from a Signal + matched Target, append a state transition guarded by an expected version and the caller's lease generation (the new state persisted atomically with its transition record), append a remediation attempt (idempotency key written before execution), resolve that attempt's approval and record its outcome, and read incident history (by id, by target, most-recent-N) for ChatOps/RAG/eval consumers.
- Introduce Alembic for migrations. There is currently no migration tooling in the project (`Database.create_database` is a no-op stub); one is needed before a real schema exists, since ad-hoc `create_all` calls don't handle production upgrades safely.
- **BREAKING**: removes the dead `alerts` table and the `SignalStore` port (superseded by `IncidentStore`, since signals themselves are not independently persisted, only as the trigger embedded in an Incident). The `alerts` table is pre-existing unused scaffolding. `SignalStore` is **not** unused: the Alertmanager webhook route depends on it, and `signal-ingestion` and `project-structure` both spec it as a requirement. Removing it therefore modifies those two capabilities rather than deleting dead code, which is why they are listed under Modified Capabilities below.
- Wire the webhook route to this store, so the capability has a real consumer: an accepted alert is normalized to a `Signal`, resolved to a `Target` via `target-inventory`'s matcher, and persisted as an `Incident` in `received` state. This is *intake*, not orchestration: it creates the incident and stops there. Nothing decides what to do about it until the Director (stage 4) exists. A signal that resolves to no target, or to more than one, is rejected at the boundary and no incident is created, since an incident with no target is not actionable by any later stage.
- Add read routes for incident history (`GET /api/v1/incidents/{id}`, `GET /api/v1/incidents`), which is what makes the persisted state observable end-to-end before a Director exists. These are the deterministic reads ChatOps (stage 10) will later consume through the same port.

## Capabilities

### New Capabilities
- `incident-store`: Postgres-backed persistence for incident lifecycle state and remediation outcomes, exposed as a domain port for the orchestrator (stage 4), ChatOps (stage 10), and the eval harness (stage 12) to build on directly. The diagnosis agent's RAG layer (stage 8) will consume this data indirectly, via whatever indexing step feeds its still-undecided vector store, not by querying this port as its retrieval source.

### Modified Capabilities
- `signal-ingestion`: its `SignalStore` port and `InMemorySignalStore` are removed, and the webhook route now creates an `Incident` through `IncidentStore` instead of storing a bare `Signal` in a process-local dict. Idempotency moves from the in-memory dict keyed by `signal.id` to the unique constraint on `incidents.signal_id`, so it survives a restart, which the dict never did. The response body changes from `signal_ids` to per-alert incident results.
- `project-structure`: its "storage seam is declared as a Protocol" requirement names `SignalStore` with `add`/`get`. The storage seam is now `IncidentStore`. The requirement itself (a Protocol at the storage seam) stands; only the name and shape change.
- `target-inventory` is consumed as an input and is not modified: `match_target` is called as it exists, with no change to the matcher or the schema.

## Impact

- **New**: `yubarta/incident/` (domain model, lifecycle enum, errors), `yubarta/infra/db/unit_of_work.py`, Alembic config + first migration, `IncidentStore` port, `SqlAlchemyIncidentStore` repository, incident read routes, `dev/inject_alarm.py` driver script, tests under `tests/incident/`, `dev-docs/dev.md`.
- **Modified**: `yubarta/infra/db/orm.py` (drop `alerts`/commented `remediations`, add `incidents`/`incident_transitions`/`remediation_attempts` tables), `yubarta/infra/db/initialization.py` (`create_database` becomes a real Alembic-driven or metadata-driven bootstrap), `yubarta/infra/db/repository.py` (replace placeholder), `yubarta/domain/ports.py` (replace `SignalStore` with `IncidentStore`), `yubarta/ingestion/routes/webhook.py` + `dependencies.py` (create incidents instead of storing signals in memory).
- **Deleted**: `yubarta/ingestion/store.py` (`InMemorySignalStore` has no seam left to fill once the storage port is `IncidentStore` and the real store is Postgres-backed).
- **Dev rig**: the dev rig does not currently start. `docker-compose.dev.yaml` and the `Dockerfile` build a Rust `director` service whose sources were deleted by `cleanup-and-foundation`, and `tests/conftest.py` imports a `start_mappers` function that no longer exists, which fails collection for the whole suite. Both are fixed here, because this change's tasks cannot be verified against a raised stack otherwise.
- **Dependencies**: adds `alembic` to `pyproject.toml`, pinned to a full `major.minor.patch`.
- **Not in scope**: the orchestrator/state machine driver itself (stage 4, `remediation-loop`), acquiring/renewing/expiring the ownership lease and incrementing `lease_generation` (stage 4; this store enforces the token but never takes a lease), Kafka topic design and work distribution (Kafka is the messaging layer, Postgres is not the queue), ChatOps read endpoints (stage 10), RAG indexing of incident history (stage 8). This change only makes the state durable and queryable; it does not decide when transitions happen.
